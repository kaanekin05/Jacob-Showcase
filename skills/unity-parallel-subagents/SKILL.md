# Dispatch parallel Unity subagents with file ownership and no Editor access

A subagent does not see this conversation. Put the file ownership and the hard rules in the dispatch prompt itself. Keep the Editor, compiles, and MCP wiring with the lead.

While a Unity test run holds the Editor, dispatch the slices that need no Unity at once. Do not wait for the run to end. Their prompts still say the lead compiles and runs the tests, and the lead makes no Unity call until the run returns.

When the user asks to run subagents for the remaining jobs, dispatch one subagent per independent job in a single message. Do not implement those jobs inline in the lead's context. Before the dispatch, run `git status --short -- <each target path>` and confirm every target is clean. A dirty target may hold another session's uncommitted edits. Hold that slice and ask the user before dispatching it. When the user asks for cheaper models, dispatch the implementers with `model: "sonnet"` and keep the lead on the session model. The lead still reads every returned diff, because the cheaper model implements and does not review.

Write each job's brief to a file in the plan's ledger folder, such as `.superpowers/sdd/<plan>/task-N-brief.md`. The dispatch prompt names that brief path and a report path, `task-N-report.md`. The subagent returns only status, files changed, one test line, and concerns. The full report stays on disk for the lead to read. The lead keeps only the prefab, scene, and wiring work, and it takes that work while the subagents run. Split the remaining jobs into two lists before you dispatch: code work an agent can finish, and human-only work such as credentials, art, device checks, and playtests. Dispatch only the first list. Name the second list in the report, with the reason a person must do each item.

Every dispatch prompt states:

- The files that subagent may edit, and the files owned by other subagents it must not touch.
- No Unity runs, in batchmode or in the open Editor. The lead compiles and runs tests.
- No edits to .prefab, .unity, or .asset files. The subagent lists the wiring it needs instead.
- No commits, staging, or git state changes.
- The failing-first EditMode test to write, or a plain statement that the task cannot be tested without a scene. A subagent with no Editor access never sees that test fail. Its report must say so and give the predicted failure. The lead treats a test never seen red as unverified until the first Unity compile. A value the subagent computed outside Unity, such as a pinned hash, is also a claim until that first run confirms it. Name the value in the report, so the lead knows what to check.
- Every source the owner has ruled out, by path, such as mockups, prototype HTML, or design exports. A subagent does not know the owner's ruling unless the prompt names it.
- The reference file to copy, by path, when a slice builds something that already exists in a sibling project, such as a build script or a config. Tell the subagent to copy it, never to rebuild it from a skill's description. A script written from a description carries guessed keystore key names and profile settings. Check the reference's real values before you accept the slice.

When a wave of subagents has returned, the lead runs one compile and the EditMode tests for the whole wave. Start with a `refresh_unity` compile request, then poll `mcpforunity://editor/state` until it is ready. Then run `run_tests` for the touched test group and read `get_test_job` to the end. Report the counts. A subagent's own claim of green does not count.

When the subagent returns:

- The lead applies the listed wiring through the Editor tools, then compiles and runs the EditMode tests.
- The lead reads the subagent's diff against the project's coding rules before accepting it.
- Recompute any number the subagent wrote into a scene or prefab from the source at HEAD before you accept it. Read the container size, anchors, and offsets from the file itself. A rewrite that looks right can still carry a wrong offset. On 2026-11-03 the lead checked a Sonnet agent's prefab rewrite this way, and the size and offsets matched HEAD.
- Hold the compile until the last subagent in the wave has landed. A file another subagent is still editing fails the compile for the wrong reason.
- While a wave is still editing, the open Editor reloads on each landed file, and MCP calls fail during the reloads. Do not stack Unity calls during the wave. Before each Unity call, read `mcpforunity://editor/state` and confirm `data.compilation.is_compiling` is false.
- A reviewer or verifier dispatch names the exact diff to read, such as `git diff --cached`, and lists the files by slice. Without that, it reviews the working tree and can miss the staged change. Untracked new files never appear in `git diff --cached`, so for them build one package per file with `git diff --no-index -- /dev/null <file>` into the ledger folder, and name that package in the dispatch. Give it the contract (the spec sections and what counts as a blocker) and the known out-of-scope items. Tell it to assume the author is overconfident, and ask for findings ranked BLOCKER, HIGH, MEDIUM, LOW, each with file and line. For a re-review after a fix pass, give it the numbered fix list and ask for ADDRESSED or NOT ADDRESSED per item with file and line, then any new breakage in the same ranking. Name the items to check hardest. Say that the compile and test counts are already reported, so it does not re-run them.
- If two subagents need the same file, one owns it, and the other lists its change for that owner. A fix round on a file a slice already owns waits until every other implementer still running has reported. A new-file slice may run beside a reviewer of another slice when it writes only new files, so the lead sends the fix round after the new-file slice reports.
- Do not edit a file while a running reviewer or verifier reads the same tree. Hold the fix until its verdict returns, then apply every finding in one pass.
- Before you act on a reviewer's HIGH finding, open the cited file and line and trace the claim yourself. Accept it, reject it, or narrow it on that reading, and say which. When the claim is about how git or a tool behaves, reproduce it in a scratch directory first. An implementer's report called a merge path safe. A reviewer's repro showed it was not. A teammate's audit report gets the same check before the lead writes it into the ledger as CONFIRMED. Open each cited line and grep the live code. On 2026-11-05 a teammate's `||` bug sat in a `/* */` block, so the lead re-checked the live block before it recorded the finding.
- Triage a review in three buckets. Send every Important finding back in one numbered fix round. Park each Minor in the ledger with the trigger that would make it matter, such as a wrong value on a real file. Record each accepted judgment on the implementer's concerns too. Fix a Minor in the same round when it can reach a shared artifact, such as an upload target, a shipped build, or a device install. Before each later review, re-check every parked Minor against the setup as it now stands. A parked item can turn real once the setup shows its trigger, so move it into the fix round then.
- After a fix round, the lead reruns the suite itself. Ask for a new review when a fix does not map cleanly to its finding, or when it changes core behaviour, such as a merge path or a guard's failure mode. A small fix the lead has traced line by line needs no second reviewer.
- Put the slice with the riskiest logic on the strongest model. The cheaper model gets the rest, unless the user asked for cheaper models across the board.
- When the user says to continue, keep moving through review and fix rounds without pausing between them. Stop only for a decision that belongs to the user, or for a blocker you cannot clear. Post one status line per round, not a full report at each step.
- When a finding turns on runtime behavior the source cannot settle, such as culling or raycast hits, measure it in Play before you change anything. On 2026-10-30 the verifier said it could not confirm a raycast drop from managed code. A live raycast on the box settled it, and the flag was not changed.
- A subagent that stops on its turn limit, or on the account usage limit, keeps its context and the work it saved. Resume it with `SendMessage` to its agent ID instead of dispatching a new one. A usage-limit stop arrives as a `failed` notification that names `rate_limit` and a reset time. Send the resume only after that time. The lead cannot wake itself at the reset. Tell the user the reset time, and ask them to send a message such as "continue" once it has passed. Then resume the agent with `SendMessage`. Do not Read or tail the subagent's output file, because it is the full transcript. Wait for the completion notice. Restate the hard rules in the resume message, list the fixes as numbered items, and ask it to finish any half-written edit. Ask for files changed, what it could not do, and each test's expected failure. Check that nothing is half-written before you compile.
- Size each dispatch to one slice that fits a 20-turn budget. On 2026-10-30 a solver subagent stopped at its 20-turn limit with no report, so split any slice that needs more turns and ask for an interim report. Count numbered items as well as files. On 2026-10-31 a fix pass with numbered items up to 17 stopped at its 20-turn limit partway through the list. Split a long list into batches of items that share files, and dispatch each batch as its own slice.
