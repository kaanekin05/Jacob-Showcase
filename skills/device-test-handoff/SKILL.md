# Device test handoff

When the user is the one tapping on a device, plan the run as numbered steps, read the logs yourself, and never change device state while the user is mid-run.

- Lay out the run as numbered steps. Each step names the user's action and the one log line you will check after it. Wait for the user's "ready" before any reset.
- Do not run `adb uninstall`, `adb install`, `adb logcat -c`, or a force-stop while the user is between steps. Those erase the state under test. Put a reset in its own tool call, never bundled with a report edit or a log dump.
- Dump the log before reading it: `adb logcat -d -s Unity > <run>_raw.txt`, then filter the tag into a second file. Work from the saved file so the result can be re-checked.
- Never wait on a streaming logcat read in the foreground. `adb logcat -s Unity -m 1` blocks until a match, so a missing line runs into the 90-second tool timeout and the shell is moved to the background. Poll the dump with a fixed cap instead: `for i in $(seq 1 30); do L=$(adb logcat -d -s Unity | grep -m1 '<pattern>'); [ -n "$L" ] && break; sleep 1; done; echo "$L"`. Give that call a 60-second timeout. If a reader was backgrounded anyway, stop it with TaskStop before any reinstall.
- To capture one app start after the user says done, record `T=$(date '+%H:%M:%S')` and run the restart in its own call: `adb shell am force-stop $PKG`, then `adb shell monkey -p $PKG -c android.intent.category.LAUNCHER 1`, then sleep about 30 seconds. In the next call, dump the log and keep only the window with `awk -v t="$T" '$2>t'`. Logcat times are zero-padded `HH:MM:SS.mmm`, so the string compare on field 2 selects the window correctly.
- When the user asks for an uninstall or reinstall, dump the log into the run file first, in its own call, then reset. The dump is the save point for the attempt.
- Before any uninstall on Android, find where the game keeps its saves. A Unity save written through `Application.persistentDataPath` lives on external storage at `/sdcard/Android/data/$PKG/files`, not in the `run-as` internal dir. Back up both: `adb shell run-as $PKG tar cf - . > internal.tar`, and `adb pull /sdcard/Android/data/$PKG/files`. Also copy `/sdcard/Android/obb/$PKG/` if it exists. Confirm the backup is non-empty, and check that the file names match the save code, before you uninstall. An uninstall deletes the external save directory too.
- After a clean install, warn the tester before step 1 that Android's first-launch notification permission dialog pauses the game until it is closed. Expect a stalled-looking first log, and check the foreground activity before you read it as a hang.
- Confirm the reinstall before you launch. Run `adb install <apk>` alone and check its exit code. Then run `adb shell pm path $PKG` and expect a `package:` line. Never chain install into `| tail -1`, because the pipe hides a failed install. An uninstall with no reinstall leaves the game absent, and the next launch does nothing.
- Before asking the user to act on a network or focus condition, probe the device. Use `adb shell settings get global airplane_mode_on` and `adb shell ping -c1 -W2 8.8.8.8` for connectivity. Use `adb shell dumpsys activity activities | grep topResumedActivity` for what is in front. A VPN app in front keeps the game from regaining focus, so focus-gated code will not run. Check this before you wait on it. To confirm the VPN itself is up, run `adb shell dumpsys connectivity | grep -oE "ni\{[A-Z_]+ [A-Z]+" | sort | uniq -c`. A `ni{VPN CONNECTED` line means the tunnel is up, and `ni{WIFI CONNECTED` shows the underlying network.
- Count before you claim: use `grep -c` or `sort | uniq -c`. Quote the decisive line exactly.
- A line that should appear and does not: grep the package source under `Library/PackageCache/` for the log string and its gate. Report "absent by design, gate: <condition>" or "absent, cause not found". Never just "absent".
- A log line shows what the SDK decided. It does not show what the screen draws. For any UI row (a button visible or hidden, a popup open or not), mark the row as the log verdict until the user confirms the screen. Ask the user to look at the screen before you write PASS. If the user's on-screen result disagrees with the log, report both and check the device state first.
- If a check needs a console the user cannot open (ad network, analytics, store), do not ask again. Mark it `blocked: needs console access` in the report and continue with what the device shows. Ask once, before step 1, which consoles the tester can open. A row whose console is closed stays `BLOCKED` even when every log line matches. It never becomes `PASS` on the logs alone.
- When a vendor console is closed, that SDK's own logcat tag is the stand-in. For Firebase, dump `FA` and `FA-SVC`. Record the stand-in line in the report row, and say which console it replaces.
- To verify a consent withdrawal, read the SDK state change, not the form closing. Expect `Setting app measurement enabled (FE): false` in the `FA` tag. Then count `Logging event:` lines with `origin=app` after that time, and expect zero. One `origin=auto` event such as `_dcu` can still appear after the withdrawal and is not app data. Quote the state line in the report row.
- If the user says a dashboard is still empty, ask them to recheck once before suspecting the build. Dashboards can lag by a few seconds.
- Scripts that `replace` a row in a report are not idempotent. Re-running one duplicated a row. `grep` for the row before re-applying.
- When a run depends on an external condition the user must change between attempts (VPN exit, locale, account), change one condition per attempt and wait for "ready". Agree on a cap before the first attempt and stop at the cap.
- When the user asks whether a reset step is needed, and the test is cheap, run the reset and read the result. Do not answer "no" from reasoning. A wrong "no" costs more rounds than the test.
- Before reading results, name the build on the device: APK path, version, and the branch and commit it came from. When the user asks which branch a build came from, check the source tree and answer from what you found. Never answer from memory.
- Clear an Android property with a real value, never an empty one. `adb shell setprop log.tag.FA ""` prints the usage line and changes nothing. Set the tag back with `adb shell setprop log.tag.FA INFO`, then read it with `adb shell getprop log.tag.FA`. Run this reset in its own call, apart from any log save. If the run turned on Firebase debug mode, also clear it with `adb shell setprop debug.firebase.analytics.app .none.` and read it back with `adb shell getprop debug.firebase.analytics.app`. Left on, the device stays in Firebase debug mode after the run.
- A blanket grant such as "you can control anything through adb" covers uninstall and reinstall for a clean start. Dump the log first, in its own call, then reset. Ask again only for steps outside adb, such as a console change or a build. A grant covers only the reset the plan names at its step. If the plan says saves are wiped after the save check, an uninstall before that step is outside the grant. Stop and ask.
- A Unity Android build with an OBB is two files. The APK alone freezes on a black screen after launch. Before installing, check the build folder for `*.main.obb`. Install the APK, then push the OBB to `/sdcard/Android/obb/$PKG/main.<versionCode>.$PKG.obb`, and confirm the file size with `adb shell ls -l`. A test build shared as only the APK is unusable on a device.
- A blocker the user cannot clear now, such as a missing token or a console login, is not a stop. Write it to project memory as a pending item with the rows it blocks, then run every row that does not need it. A row that fails on a known blocker stays in the report as FAIL with the blocker's ID, and gets a re-run once the blocker lands.
