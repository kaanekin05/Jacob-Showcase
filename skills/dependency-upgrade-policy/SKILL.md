# Dependency upgrade policy

Stay on the current major version and try the change there first. Offer the upgrade as a conditional
next step, not as the opening action.

- Name the concrete problem that would justify the upgrade: an API that no longer builds, an SDK that
  requires the newer version, or a store deadline. If you cannot name one, the answer is to stay.
- Put the decision to the user as one question. Lead with the stay option and say it is recommended.
- Keep a major upgrade out of the feature branch. Do it as its own change, after the user agrees.
- A version bump that is not a major step (a patch or minor update) is a separate, smaller decision.
  List it apart from the major upgrade so the two are not approved together.
- Before you call an SDK stale, sweep every candidate source. Check `~/Downloads` for `*.unitypackage` files, and check the working tree, because a bump can sit uncommitted. Read the uncommitted version with `git diff -U0` on the SDK's `Dependencies.xml` or manifest. Compare each candidate with the installed version. Skip any candidate older than the installed one, and say so, rather than downgrading.
- Once a minor or patch SDK bump is approved, import one SDK at a time and commit each one before the next.
- Before importing, diff the old and new editor DLLs for build hooks (`strings -a` on `PostProcessBuild`, `UpdatePlist`, `PodfileEditor`). A newer SDK can move iOS build logic out of the DLL into a loose editor script in the package. Carry that script over, or the platform setup is lost without any error. Then compare the exported `Info.plist` keys with the baseline plist. A dropped key stops the step, even when the build passes. If the carried script forces a linkage change, such as dynamic pods, do not edit the vendor file. A re-import silently reverts that edit. Add a project-owned Editor post-build script that restores the linkage, ordered after the vendor hook and before `pod install`. Facebook 18.1.1 rewrites the Podfile at post-build order 45, and Google EDM runs `pod install` at order 50, so a guard at order 47 fits between them. Roll the step back and mark it blocked only when no guard can restore the setting.
- Test a Podfile guard offline before the Editor run. Replay the vendor's rewrite regex, then your restore regex, over the exported Podfile text. Run it once with LF endings and once with CRLF. The round trip must return the original text, and the restore must match in both cases.
- When the user asks to keep only the package's post-build scripts, leave those scripts unmodified. Add a project-owned script only for a break you can name, and say which break it fixes.
- Exclude what the project already owns: bundled resolvers, sample IAP code, example scenes.
- Before an SDK bump, grep the project's own `[PostProcessBuild]` hooks for consent and tracking keys, such as `GOOGLE_ANALYTICS_DEFAULT_ALLOW_*`. A hook with a later order runs after the vendor hook, so any value it writes to those keys wins. Consent keys belong to the vendor's consent flow, so a project hook should not write them. Keep the ATT and SKAdNetwork keys, and name any removal in the commit body.
- When an SDK's changelog or adapter comment names a dependency's version line (for example, "Nefta SDK 4.6.x"), pin the newest release on that line. The newest release overall can fail to compile. Confirm the adapter's method signatures against the candidate, then compile both platforms. Check each signature, not only the name. Take the call lines the adapter makes and grep each declaration in the candidate's source. A declaration grep that matches nothing usually means a bad pattern, so retry with a plainer one before you conclude anything. A name match alone is weak evidence.
- After you add a package line to `Packages/manifest.json`, parse the file before you open the Editor: `python3 -I -c "import json;d=json.load(open('Packages/manifest.json'));print(d['dependencies'])"`. A `sed -i ''` edit on macOS can leave a broken or misplaced line, and the parse catches it before package resolution fails.
- Sample folders can define a class with the same name as a project class. If a game script fails to compile after a filtered import, check for that shadowing before you blame the SDK version.
- Back up the project's SDK settings asset before the import, then `cmp` it afterwards. Keep the project's copy.
- Packages can ship feature switches defaulted off, such as `#if false // MODULE_MARKER` or `#if false // TEXTMESHPRO_MARKER`. Before the import, record each marker line with its line number and line ending (CRLF or LF). After the import, restore those lines by line number and diff the markers against the record. The import overwrites them without any error.
- Count `+guid` lines in `git diff -U0` after the import. Only known `.meta` churn is acceptable. Any other GUID change stops the step.
- A changed `.meta` GUID is safe to keep only after `grep -rlF` on the old and the new GUID finds no `.unity`, `.prefab`, `.asset`, or `.cs` reference. Record the grep result in the step report.
- When a package ships an existing asset path under a new GUID, keep the old GUID. Copy the new bytes over the existing file, keep its `.meta`, and change only the version label in that `.meta`. Scene and prefab references then stay valid, and the `+guid` count stays at 0.
- Save the SDK's file manifest before the import. After the import, list the files the new version dropped with `comm -23 <(sort old_manifest) <(sort new_manifest)`. Delete each dropped file that still exists, with its `.meta`, through `git rm`. Vendors can swap a static library such as `.a` for an `.xcframework`. A leftover `.a` then risks duplicate symbols at link time.
- An SDK import can also roll a bundled dependency backwards. A MAX SDK 13.6.4 import overwrote the bundled External Dependency Manager 1.2.189 with 1.2.186, and it rewrote the `.meta` GUIDs. After any import, compare the top `# Version` line of each bundled dependency's changelog with HEAD. A downgrade is a stop. Keep that dependency out of the SDK commit. Restore it with its `.dll`, `.meta`, and docs only on the user's yes.
- Before you commit a native SDK bump, read the pins that its mediation adapters declare. Fetch each adapter's podspec or Gradle deps for the adapter version you ship. An adapter that pins the old SDK line blocks the iOS pod resolve once the SDK moves past it. AdMob 11.5.0 needs Google-Mobile-Ads-SDK `~> 13.9`, while the MAX Google adapters pin `= 13.3.0`. Name that break in the commit body and the report, and list the adapter bump as its own step.
- A package's declared minimum can be older than the API its code calls. Grep the package source for the newer API's symbols. Confirm each one exists in the cached copy of the version you ship, at `Library/PackageCache/<package>@<version>`. Check which version a sibling project on the same package runs. Name the gap in the report. A compile on the shipped version is the only real check.
- Resolve native Android dependencies once, after every SDK in the batch has landed, then compile and build.
- Triage an Android build break after an SDK bump offline, with Unity's bundled Gradle. Run the `gradle-launcher` jar from the Unity install's `PlaybackEngines/AndroidPlayer/Tools/gradle/lib` folder, with that folder's `OpenJDK` as `JAVA_HOME`. Use `--offline -q :launcher:dependencies --configuration releaseRuntimeClasspath`, run from the project's `Library/Bee/Android/Prj/IL2CPP/Gradle` folder. Find the failing artifact in the output, and read the top-level line above it to see which SDK pulls it in.
- A transitive androidx library can need a newer Android Gradle plugin than Unity ships, and then the build fails at resolve. Find the bump that introduced it with `git log -S '<artifact>' -- <Dependencies.xml>`, and compare the pinned version before and after. Name that bump in the report. Fixing it is a separate step the user approves.
- Roll back a failed step by path, not with a repo-wide reset: `git restore --staged --worktree --source=HEAD -- <paths>`, then `git clean -fdq -- <paths>`. Confirm the paths match the last good commit, then mark the step `(blocked: <reason>)` and continue.
- With Google EDM's Swift Package Manager off (`Google.IOSResolver.SwiftPackageManagerEnabled` set to `False` in `ProjectSettings/GvhProjectSettings.xml`), Firebase arrives as a CocoaPod. A Podfile patch that dedupes GoogleUtilities is right only when Firebase comes through SPM, which carries its own copy. Under CocoaPods, make that patch skip itself when the Podfile contains `pod 'Firebase/`, and name the switch in the commit body.
- An iOS build that fails on a duplicate `AppLovinSDK` after a mediation bump can mean EDM resolved the SDK twice, once through SPM and once as a CocoaPod. Check the same `SwiftPackageManagerEnabled` switch first. Get the user's yes before you change it, because it alters how every Google iOS dependency resolves.
- Finish a batch with both platform builds: a dev APK build, checked with `aapt dump permissions`, and an unsigned `xcodebuild` of the exported iOS project. Compile alone does not show that permissions, pods, and `Info.plist` survived the import.
- When the user is away and asks you to run the approved plan, run the bumps in order, commit per SDK, and end with a list of what was skipped and why.
- A target API level bump (`AndroidTargetSdkVersion` in `ProjectSettings/ProjectSettings.asset`) is its own decision, not part of an SDK bump. Commit it alone, and only on the user's yes. Before the commit, name the new level's platform behavior changes from the platform's own release notes, and list them as checks for the next device build. Do not state them as verified from memory.
- Before you keep an old package beside its replacement, grep the new package for the old one's build hooks and exporters. A package that ships its own `IPostprocessBuildWithReport` hook makes a kept old copy run that hook twice. Remove the old package in the same change, and name the removal in the commit body.
- When an SDK adds a grant or revoke path that the shipped build never had, the new revoke changes what paying players keep. Keep the shipped behavior by default. Put keep-or-drop to the user as one decision, name the recommended option, and say what a false revoke costs the player and what the code change removes. Apply the user's answer as written.
- A temporary define that bridges an API gap, such as `MAX_NEFTA_DISABLED` for a Nefta call the installed adapter lacks, is a shortcut. Mark it `// SHORTCUT:`, name the upgrade that removes it, and put that removal in the commit body so the define does not outlive the gap.
- A code default change does not reach a live value already set in Remote Config. When you flip a default in code, name the console key, the value, and each platform it applies to, and ask the user to set it. Say that the code change alone leaves the live behavior unchanged. Keep the key shipped builds read.
