# Git workflow: commit by path, merge one way, and wire GUI diff tools

Stage by explicit path, then commit in the same call. Never `git add -A` or `commit -a` in a shared tree, because another session may hold uncommitted work.

## Scoped commits by path

- The procedure lives in `commands/commit-slices.md` Step 4, where the repo has it. Read it and follow it, even for one slice.
- Build slices with `git status --short -uall`, never the bare form. Check the staged set with `git diff-index --cached --name-only HEAD` before each commit.
- A failed `git add` stages nothing. A failed staged-set check leaves the paths staged, so do not re-add them.
- A path that an earlier `git rm` already staged cannot appear in a later `git add`. Git fails the whole call with `pathspec ... did not match any files`, and a chained commit never runs. Drop that path from the add, and keep the removal in the index.
- The index can already hold staged paths before you start, left by an earlier session. Run `git diff --cached --name-status` first. Unstage every path outside the slice with `git restore --staged -- <path>`, then stage the slice. Otherwise those paths ride into your commit under your subject.
- When commits are banned but each task needs a reviewable diff, record checkpoint commits from a temp index. HEAD and the real index stay untouched.
- A commit hook can check the whole working tree, not the commit. A peer session's failing check then blocks your commit even when your staged files are clean. Read what the hook runs before you assume staging alone is enough.
- Attribute a failing check before you fix or report it. For each file the check cites, run `git status --short -uall` and `git diff -- <path>`. A file you did not touch belongs to a peer session. Report its owner and its uncommitted state. Do not stage or revert their hunks to clear the check.
- A hook can also rewrite working files, such as a lock file. Leave hook-made changes unstaged when they describe nothing in your slice. When the lock describes a skill in your slice, stage the lock with that skill. `sync-autoharness-lock.sh` counts a skill's files, so a commit that carries `SKILL.md` without its lock entry leaves the lock claiming a file count the commit does not hold. Stage the skill's `.ledger.jsonl`, `.sidecar.json`, and any new evidence file the hook wrote, with the lock. Check `git show --stat HEAD` afterwards.
- A plugin can leave per-session runtime state in the tree. autoharness writes `.claude/autoharness/session-*` and a `.lock` file inside each project it runs in. `git status --short -uall` lists these as `??`. They are never part of a feature commit, so stage by path and leave them out. A memory plugin does the same. `.memsearch/` holds `.index.pid`, state JSON, and daily notes that it rewrites during a session. Never `git add` a runtime folder such as `.claude/` or `.memsearch/` as a whole directory. Name the real files, and report the folder as a `.gitignore` gap for the user to decide. The same state can sit inside an evidence folder. A device-test report folder held `sdk-test/2.8.1/.claude/autoharness/` lock and session files. Build a folder's path list with `find DIR -type f -not -path '*/.claude/*'`, not a bare `find`, and confirm the staged list has no `.claude/` entry.
- A hook that rewrites a lock file on every run churns after each commit. The lock's `updated_at` and `file_count` change again, and an evidence file appears mid-commit. Do not re-commit to chase it. Stop after the commit that carries your change, and batch the lock and evidence drift into one commit at session end.
- To commit only your own hunks from a file another session also edits, build a blob from `git show HEAD:<path>` with your lines inserted. Write it with `git hash-object -w`, then stage it with `git update-index --cacheinfo <mode>,<hash>,<path>`. Read `<mode>` from HEAD first with `git ls-files -s <path>` (or `git ls-tree HEAD <path>`), and pass it through. Never hard-code `100644`: a script that is executable in HEAD (`100755`) gets its executable bit silently dropped, and the commit shows a mode change nobody meant. Your working-tree edits and the peer's hunks stay as they are.
- To split one shared file into several commits, cut each slice's hunks from `git diff -U0 -- <path>` by their `@@` start line. Write each slice to a patch, then dry-run it with `git apply --cached --check --unidiff-zero <patch>` before any commit. Attribute hunks first with `git diff -U0 -- <path> | grep '^@@'`. The text after the second `@@` names the enclosing function. Once an earlier slice has shifted line numbers, select hunks by that function name, not by start line. Apply one patch per slice, check the staged list, and commit in the same call. When a slice must build without the peer's uncommitted code, export the staged index with `git checkout-index -a --prefix=<tmp>/` and run the tests inside that export. A working-tree test pass proves only that the peer's code is present, not that HEAD works.
- Before committing, compare `git diff-index --cached --name-only HEAD | sort` with the expected list. Do not use `git diff --cached --name-only` for this, because the rtk hook drops lines from it. If you do use it, add `--no-renames`. A file deleted and re-added with identical content shows as one rename, and the old path drops out of the list. Then read `git diff --cached --numstat`. Commit in the same call. When a staged file sits next to a credential, such as a signing config, grep the staged files for the literal secret value before the commit. Read the value from its gitignored local file in the same shell, count hits with `grep -cF`, and never print the value. Expect 0 hits.
- Scope the commit to the request's files, not to every dirty file that looks related. Read each candidate's hunks with `git diff -- <path>` first. Leave out a hunk that flips a project-wide setting (a `ProjectSettings/*.asset` flag, for example) or deletes a file the request never named. Leave it unstaged, name it in the report, and ask whether it gets its own commit. A commit request covers that request only. Make no follow-up commit without a new yes. Before a slice goes in, check that each symbol, key, or file it references exists at HEAD, for example `git show HEAD:<path> | grep -c <symbol>`. A slice that references a peer's uncommitted hunk leaves HEAD unable to run. Name that dependency in the report, and commit only on a yes that accepts the broken-HEAD window.
- A diff that empties a config file is a stop, not a slice. Compare `wc -c` with the file's size at HEAD. A file cut to a few bytes has lost its keys, such as app IDs or `SetupDone`. Name the lost keys and ask before any commit or restore.
- A Unity package import can write into the tree in the middle of a session, with no edit from this session. Treat those files as not mine. Name them in the report and leave them unstaged until the user says whose they are.
- Before you slice a vendored file that changed mid-session, read the top `# Version` line of its changelog at HEAD and in the working tree. A file that moved to an older version is a stop, not a slice. Restore it only on the user's yes, and restore its `.meta` with it, because an import can give the `.meta` a new GUID.
- Get every count you report from the staged list (`git diff-index --cached --name-only HEAD | wc -l`), not from memory of an earlier listing. A recalled count drifts after a restore or a re-import.
- A file can show as modified only because of line endings. NuGet writes CRLF into `Assets/Packages`, and git normalizes it away. Confirm with `git diff --ignore-cr-at-eol --numstat HEAD -- FILE`. Zero lines means EOL-only: leave it unstaged, and name it in the report. Drop it from the expected list before the staged-set check.
- When the user asks to commit everything separately, group the dirty tree by feature and write the group list first. Commit each group in its own call. Then rerun `git status --short -uall` and commit any stragglers under their own subject. A `.meta` file left outside its group is the usual straggler. Commit everything does not widen the set of files. Runtime state from the autoharness and `.memsearch/` bullet never joins a group. An EOL-only file from the line-ending bullet never joins a group either. Leave both unstaged and name them in the report.
- A pre-commit doctor that passes after the hook's own lock sync says little about the committed tree. The sync rewrites `skills.lock.json` before the check, and that can clear earlier lock failures. Report the sync as a separate fact, and leave the rewritten lock unstaged when it describes a peer's skill churn.
- Skip the hook with `--no-verify` only on the user's explicit yes. Name the failing checks in the commit body.
- To commit one path while a peer session has other files staged, use `git commit --only -m "<subject>" -- <path>`. It commits that path alone and leaves the peer's staged files out. It takes each path's working-tree content, so it also commits a peer's uncommitted hunks in that same file. Use `--only` only for files with no peer hunks. For a shared file, use the blob method above. When the pre-commit doctor checks a lock hash, `--only` can fail on a hash mismatch: it runs the hook against a temp index that lacks a peer's intent-to-add (`git add -N`) entries. Then build the commit from the real index. Run `git diff --cached --name-status` and unstage every path that is not yours with `git restore --staged -- <path>`, then name those paths in the report. Keep only your hunks in a patch cut from `git diff HEAD -U0 -- <path>`, apply it with `git apply --cached --unidiff-zero <patch>`, and check the staged list against the expected list before `git commit -F`. Re-stage the unstaged paths after the commit.
- A commit can fail with `cannot lock ref 'HEAD': is at <A> but expected <B>`. A peer committed while the pre-commit doctor hook ran. Run `git log --oneline -3` and `git diff --numstat HEAD -- <path>` to confirm your change is still there. Then retry the same `--only` commit once against the new HEAD. Do not reach for `--no-verify` to get past a lock race.
- A peer's plain `git commit` takes the whole shared index, including entries you staged with `git update-index` or `git add`. The window is your pre-commit hook: it runs after staging and before the commit is written. If your commit then fails with `no changes added`, run `git log -1 --stat`. When your paths sit under a peer's subject, your content is already in HEAD with the wrong message. Do not amend or rewrite shared `main`. Report the hash, the peer's subject, and the file list, then leave the peer's uncommitted hunks alone.
- The opposite race also happens. A peer's `git update-index` or `git add` during your pre-commit hook can replace the blob you staged for the same path. Your commit then carries the peer's content under your subject. For a shared path, build the real commit from a private index outside the repo: `export GIT_INDEX_FILE=<tmp>`, `git read-tree HEAD`, `git update-index --cacheinfo <mode>,<hash>,<path>` for each blob, then `git commit` with the same variable set. No peer can write that index. After the commit, run `git show --stat HEAD` and compare it with the expected list before you report success. A mismatch goes in the report. Do not amend shared `main`.
- After a private-index commit, the shared index still holds the pre-commit blob for your paths. Git shows that as a staged reversal. Point only those entries at the new HEAD blob (`git ls-tree HEAD <path>`), and only when the shared index still holds your old blob. If it holds anything else, a peer has staged there, so leave it. If you ran `git add -N` on a new folder before the commit, the shared index also keeps those intent-to-add marks for your paths. They show as staged deletions after the commit. Clear them with `git reset -q -- <your paths>`, then confirm `git status --short -uall -- <your paths>` is empty.
- The zsh path trap, the checkpoint recipe, and the rest of the rules are in `references/scoped-commits.md`.

## Merging dev into release (Unity repos)

- Merge one way only: `dev` into `release`. In repos whose release branch is `main`, the same rule applies to `development` into `main`. Never merge `release` back into `dev`. Never push unless the user asks.
- Before any merge into `main` or `release`, list what the merge adds: `git diff --name-status --diff-filter=A <target>..<source>`. Screen every added path for signing keystores (`*.keystore`, `*.jks`), `.env` files, and credential or token files. A fast-forward moves them onto the release branch with no merge commit to inspect. If one shows up, stop and report it before the merge. Check `git status --short -uall` is clean before any `git checkout` of the target branch. If the checkout still fails with "would be overwritten by checkout" after the tree looked clean, a plugin wrote a file after your commit. Do not retry the checkout. Move a branch you are not on with `git branch -f <name> <sha>`, and only after `git merge-base --is-ancestor <name> <sha>` confirms a fast-forward. Never run it on the checked-out branch.
- Before a merge into `main` or `release`, confirm no background build or release is still running. A release step can commit its outputs onto the source branch when it exits. Merge only after that run has exited and the tree is clean. Otherwise the target misses those commits.
- The secret screen has a second half: the added lines, not only the added file names. Run `git diff <target>..<source> -- . | grep -E '^\+'` and count token shapes such as `ghp_`, `github_pat_`, `AKIA`, `xox[bp]-`, and `BEGIN ... PRIVATE KEY`. `grep -c` exits 1 when the count is 0. Read the count as the result. Exit 1 with `0` is a clean screen, not a failed command.
- `git rev-parse --short A B` fails with "Needed a single revision" when given two refs. Run one `rev-parse` per ref.
- Auto-resolve only version lines, tool session folders, and regenerated build outputs. Everything else is a decision: stop, list each file, and ask one conflict at a time.
- Run the release-setting checks before the merge commit. A check that cannot read its target is a violation, not a pass.
- Never resolve `ProjectSettings/ProjectSettings.asset` by taking one whole side. Resolve its version hunks line by line, and keep release's scripting define symbols.
- After any merge into `release`, diff the scripting define symbols per platform against the last clean release tag. Any debug-only symbol that appears is a stop, not a note.
- In zsh, write `"${1}:path"`, not `"$1:path"`. The bare form parses `:path` as a history modifier and passes a mangled path to `git show`.
- The full rules are in `references/dev-to-release-merge.md`.

## Wiring a diff tool into a git GUI

- A GUI app starts the tool with no terminal attached. Wrap the tool so it opens its own terminal window, and copy `$LOCAL` and `$REMOTE` to a fresh temp directory, keeping each file's extension.
- Test the wrapper by hand. Open a `.cs` file and a `.png` through the GUI before you write any config.
- Fork and SourceGit each have their own config route. Read `references/gui-diff-wiring.md` before you touch either one.
